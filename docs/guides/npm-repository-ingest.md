---
title: npm packages from Git repositories
description: Ingest tagged npm packages from GitHub or a Node Git source.
---

A VCS source can ingest npm packages from the repository root on GitHub on either runtime, or through the generic Git provider on Node. Generic Git archive building is unavailable on Workers; use the GitHub provider there. See the [configuration reference](../reference/configuration.md) for source settings. <!-- source: packages/plugin-github/src/provider.ts --> <!-- source: packages/core/src/sources/config.ts --> <!-- source: packages/core/src/ingest/vcs/git-provider.ts -->

## Names and discovery

Discovery recognizes a root `package.json` and creates an npm VCS source. Forks are skipped unless explicitly included. The manifest name must pass organization-wide claim admission before registration. Admission refuses overlapping private claims and cached public names; when an npmjs proxy exists, an exact name is also probed upstream and the probe fails closed. See the [claim rules](../reference/access-model.md#npm-claims-publishing-and-admission). Create npm repository sources through the API or discovery; import manifests refuse them. <!-- source: packages/plugin-github/src/discovery.ts --> <!-- source: packages/core/src/sources/bulk-discovery.ts --> <!-- source: packages/db-sqlite/src/repositories/registered-name.ts --> <!-- source: packages/core/src/import/manifest.ts -->

A configured `packageName` is grammar-checked when saved and compared with the root manifest at sync. Each repository supplies one root package; workspace and monorepo subdirectory packages are not discovered. <!-- source: packages/core/src/sources/config.ts --> <!-- source: packages/core/src/ingest/vcs/npm-adapter.ts --> <!-- source: packages/plugin-github/src/provider.ts -->

## Tags and manifests

Only tags selected by the source's `refs` settings become candidates. The broker strips one leading lowercase `v`, accepts valid npm semantic versions without build metadata, and deduplicates equivalent versions, preferring the exact version tag over its `v` form. Branches do not produce npm versions. `latest` selects the highest accepted stable version, falling back to the highest prerelease when no stable version remains. <!-- source: packages/plugin-github/src/provider.ts --> <!-- source: packages/core/src/ingest/vcs/git-provider.ts --> <!-- source: packages/core/src/registry/npm/version-rules.ts --> <!-- source: packages/core/src/ingest/vcs/npm-adapter.ts --> <!-- source: packages/core/src/catalogue/versions.ts -->

At each winning tag, `package.json` must have the expected name and a version exactly equal to the normalized tag version. Missing, malformed or oversized manifests are skipped with reason `invalid_manifest`; name and version differences use `name_mismatch` and `version_mismatch`. A skipped tag does not stop the remaining tags. The manifest parser bounds bytes, depth and node count and refuses duplicate or prototype-related keys. <!-- source: packages/core/src/ingest/vcs/npm-adapter.ts -->

## Archive builds

Synchronization eagerly queues `core:npm-vcs-build:v1` for versions needing an archive. An archive request for an unbuilt version also queues a build and receives HTTP 503 with `Retry-After: 10`. Builds run as leased jobs, outside the HTTP request; one version has at most one running build. The idempotency key includes a ten-minute clock bucket, so another bucket allows a new job after a terminal build left no archive. Each job allows up to three attempts. <!-- source: packages/core/src/registry/module.ts --> <!-- source: packages/core/src/registry/dist-service.ts --> <!-- source: packages/core/src/ingest/npm-vcs-build-job.ts -->

The GitHub provider fetches the tarball for the tag's commit with a 64 MiB input cap. The broker stages the repository archive, walks it to select and pack files, reopening it when uncaptured rule files must be read, and emits a gzip tarball with `package/` paths, fixed timestamps and owner IDs, and normalized file modes. It runs no lifecycle scripts; build required output before tagging, or build and publish from CI. <!-- source: packages/plugin-github/src/provider.ts --> <!-- source: packages/core/src/ingest/dist-fetch.ts --> <!-- source: packages/core/src/registry/npm/tarball-pack.ts -->

GitHub archives apply `.gitattributes` export rules; files omitted there cannot be restored by npm inclusion rules. Generic Git also applies export-ignore rules. The broker does not resolve LFS pointers: a pointer in the input archive remains a pointer in the packaged files. <!-- source: packages/plugin-github/src/provider.ts --> <!-- source: packages/core/src/ingest/vcs/git-provider.ts --> <!-- source: packages/core/src/ingest/vcs/git-tar.ts -->
<!-- verify: npm-github-archive — on a disposable GitHub repository, check export-ignore and the repository's LFS archive setting; confirm the downloaded tarball contains the intended bytes before relying on ingest. -->

The packer honors root `files`, `main`, `bin` and bundled dependencies, directory `.npmignore` files with `.gitignore` fallback, and mandatory include/exclude rules. It skips symlinks. Its supported pattern grammar is literals and backslash escapes, `*`, `?`, whole-segment `**`, non-nested brace lists of at most 16 alternatives, ASCII bracket classes, leading `!`, and leading or trailing `/`. Brace ranges, nested braces, POSIX classes and extglobs skip the version with `candidate_skipped: unsupported_files_pattern`. Publish such packages from CI instead. <!-- source: packages/core/src/registry/npm/packlist-rules.ts --> <!-- source: packages/core/src/registry/npm/tarball-pack.ts -->

Packing bounds path depth at 64 segments and compiled rules at 4 MiB. Permanent pack refusals use `unsupported_files_pattern`, `invalid_packlist`, `invalid_tarball` or `archive_changed`; they record the reason in the source's error field and end that job without retrying the refusal. These include unsupported patterns, packlist and output limits, malformed archives and invalid README controls. These reports set the source error without counting as a poll failure. <!-- source: packages/core/src/registry/npm/packlist-rules.ts --> <!-- source: packages/core/src/ingest/dist-fetch.ts --> <!-- source: packages/core/src/sources/source-error-codes.ts --> <!-- source: packages/core/src/registry/module.ts --> <!-- source: packages/db-sqlite/src/repositories/source.ts -->

After packing, promotion stores a non-refetchable archive and attachment records its integrity and root README for the version. Until attachment, metadata has no built integrity and the archive endpoint waits for a build. A build that loses attachment leaves its promoted blob for orphan collection after seven days. Back up these bytes as described in [Backup and upgrades](../operations/backup-and-upgrades.md); retaining the Git repository alone is insufficient. <!-- source: packages/core/src/ingest/dist-fetch.ts --> <!-- source: packages/core/src/registry/npm/render.ts --> <!-- source: packages/core/src/registry/dist-service.ts --> <!-- source: packages/db-sqlite/src/repositories/blob-references.ts -->
