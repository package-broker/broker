description: Ingest tagged npm packages from GitHub or a Node Git source.

A VCS source can ingest npm packages from the repository root on GitHub on either runtime, or through the generic Git provider on Node. Generic Git archive building is unavailable on Workers; use the GitHub provider there. See the [configuration reference](../reference/configuration.md) for source settings. <!-- source: packages/plugin-github/src/provider.ts --> <!-- source: packages/core/src/sources/config.ts --> <!-- source: packages/core/src/ingest/vcs/git-provider.ts -->

## Names and discovery

Discovery recognizes a root `package.json` and creates an npm VCS source. Forks are skipped unless explicitly included. The manifest name must pass organization-wide claim admission before registration. Admission refuses overlapping private claims and cached public names; when an npmjs proxy exists, an exact name is also probed upstream and the probe fails closed. See the [claim rules](../reference/access-model.md#npm-claims-publishing-and-admission). Create npm repository sources through the API or discovery; import manifests refuse them. <!-- source: packages/plugin-github/src/discovery.ts --> <!-- source: packages/core/src/sources/bulk-discovery.ts --> <!-- source: packages/db-sqlite/src/repositories/registered-name.ts --> <!-- source: packages/core/src/import/manifest.ts -->

Organization sessions with `org:sources:write` can call `POST /_pb/sources/discovery/plan` with an organization-owned GitHub App `credentialId`, its numeric `installationId`, a repository `pattern`, and `cursor: null`. Set `ecosystem` to `npm` or `composer` to select one ecosystem; omit it to inspect both. `includeForks: true` opts in to forks for either ecosystem. Planning returns package entries, fixed skip reasons and a `nextCursor`. <!-- source: packages/core/src/api/routes/source-discovery-schemas.ts --> <!-- source: packages/core/src/sources/configured-discovery.ts -->

Call `POST /_pb/sources/discovery/apply` with the same credential, installation and selection options, up to 20 repository names, and the plan's `nextCursor`. Each invocation attempts at most two repositories and rechecks their manifests. Continue with `remainingRepositories` before fetching another plan page; a rate-limited repository stays at the front of that list. The response retains `nextCursor` and reports each creation, existing source, refusal or failure. <!-- source: packages/core/src/sources/bulk-discovery.ts --> <!-- source: packages/core/src/sources/configured-discovery.ts -->

A configured `packageName` is grammar-checked when saved and compared with the root manifest at sync. Each repository supplies one root package; workspace and monorepo subdirectory packages are not discovered. <!-- source: packages/core/src/sources/config.ts --> <!-- source: packages/core/src/ingest/vcs/npm-adapter.ts --> <!-- source: packages/plugin-github/src/provider.ts -->

## Saved discovery rules

An organization session with `org:sources:write` can save a rule through `POST /_pb/sources/discovery/rules`. Supply `name`, an organization-level GitHub App `credentialId`, numeric `installationId`, and a repository-name `pattern`. `ecosystem` accepts `composer`, `npm` or `both` (the default). Forks are excluded unless `includeForks` is true. `enabled` defaults to true; `intervalSeconds` defaults to 86400 (daily) and accepts 3600 through 2592000 (one hour through 30 days). Creating a rule and replacing its credential or installation require a fresh sign-in, using the same reauthentication window as source credential writes. <!-- source: packages/core/src/api/routes/source-discovery-schemas.ts --> <!-- source: packages/core/src/api/routes/discovery-rules.ts -->

Use `GET /_pb/sources/discovery/rules` to list rules, with optional `after` and `limit` (1–100), and `GET /_pb/sources/discovery/rules/:id` to read one. Read responses include a revision ETag. Readers see configuration and completed results; writers also see credential bindings and internal progress. `PATCH` and `DELETE` on that rule require `If-Match: "rN"`. Changes to credential, installation, pattern, ecosystem or forks reset the checkpoint and start a new scan. Rename, interval and enable/disable preserve the checkpoint and results; disabling ends an active run. Deleting a rule preserves the sources it created. `POST /_pb/sources/discovery/rules/:id/run` with `{}` makes an enabled rule due on the next scheduler tick, preserving future transient and rate-limit backoff deadlines. Disabled rules return a specific conflict. Writes accept `Idempotency-Key`. `GET /_pb/sources/discovery/rules/:id/results` returns the last completed run’s outcome, counts and skip reasons, without credentials or internal cursor state. In-progress progress is stored separately. The rule stores only the latest completed summary and current progress, with at most 50 skip details and 49 pending repository names. <!-- source: packages/core/src/api/routes/source-discovery-schemas.ts --> <!-- source: packages/core/src/api/routes/discovery-rules.ts --> <!-- source: packages/db-sqlite/migrations/0010_source_discovery_rules.sql -->

Both runtimes run a minute dispatcher through the core job registry. It selects up to ten due rules; each leased rule job plans up to three repositories and processes several pending repositories when its 20-second wall-time and SQL statement budget permit. Each invocation uses the documented 450-statement chunk budget within the Workers Paid limit of 1,000 D1 queries, counting batch statements individually. It reserves 30 statements for checkpoint and finish writes and 100 before admitting another repository, allowing several repositories with both ecosystems per tick. Credentials and installation tokens are reused within one invocation. A large scan therefore spans multiple ticks. The durable page cursor and pending repositories resume the scan; a rate-limited repository stays first and waits at least five minutes before retrying, honoring GitHub backoff up to one hour. Transient failures retain progress and back off for five minutes to one hour; five consecutive failures end a run. Admission and fork checks use the same BulkDiscovery path as manual discovery. Existing sources are counted rather than duplicated. Runs never reconcile or pause existing sources; an unfinished rule-owned source resumes admission across runs after lease loss. Activation completes that admission, so an administrator-paused source stays paused. <!-- source: packages/core/src/runtime/discovery-rule-jobs.ts --> <!-- source: packages/core/src/sources/configured-discovery.ts --> <!-- source: packages/core/src/sources/bulk-discovery.ts -->

A rule belongs to the organization and continues after its creator leaves or loses permission. Runs and their source writes are audited as a system actor carrying the rule id. Disabling or deleting a rule, changing its revision, changing its organization-level GitHub App credential binding, or losing the job lease revokes write authority. Deleting a credential referenced by discovery rules is refused; remove or replace those rules first. Page-number cursors can drift if GitHub repository membership changes during a scan, causing missed or repeated entries until a later rescan. Removed, renamed and archived repositories are not reconciled with sources already created; that work remains in issue #970. <!-- source: packages/db-sqlite/src/repositories/discovery-rule-authority.ts --> <!-- source: packages/core/src/sources/source-service.ts -->

## Tags and manifests

Only tags selected by the source's `refs` settings become candidates. The broker strips one leading lowercase `v`, accepts valid npm semantic versions without build metadata, and deduplicates equivalent versions, preferring the exact version tag over its `v` form. Branches do not produce npm versions. `latest` selects the highest accepted stable version, falling back to the highest prerelease when no stable version remains. <!-- source: packages/plugin-github/src/provider.ts --> <!-- source: packages/core/src/ingest/vcs/git-provider.ts --> <!-- source: packages/core/src/registry/npm/version-rules.ts --> <!-- source: packages/core/src/ingest/vcs/npm-adapter.ts --> <!-- source: packages/core/src/catalogue/versions.ts -->

At each winning tag, `package.json` must have the expected name and a version exactly equal to the normalized tag version. Missing, malformed or oversized manifests are skipped with reason `invalid_manifest`; name and version differences use `name_mismatch` and `version_mismatch`. A skipped tag does not stop the remaining tags. The manifest parser bounds bytes, depth and node count and refuses duplicate or prototype-related keys. <!-- source: packages/core/src/ingest/vcs/npm-adapter.ts -->

## Archive builds

Synchronization eagerly queues `core:npm-vcs-build:v1` for versions needing an archive. An archive request for an unbuilt version also queues a build and receives HTTP 503 with `Retry-After: 10`. Builds run as leased jobs, outside the HTTP request; one version has at most one running build. The idempotency key includes the immutable commit, packing policy, retry generation and a ten-minute clock bucket. Each job allows up to three attempts. Permanent refusals and exhausted attempts persist a terminal outcome; later buckets do not enqueue another build for that identity. Archive requests then return HTTP 410 without retry advice. An authorized source sync request deliberately clears terminal outcomes and advances their retry generations. A changed commit or packing policy has an independent build outcome. <!-- source: packages/core/src/registry/module.ts --> <!-- source: packages/core/src/registry/dist-service.ts --> <!-- source: packages/core/src/ingest/npm-vcs-build-job.ts -->

The GitHub provider fetches the tarball for the tag's commit with a 64 MiB input cap. Staging reserves at most the configured archive ceiling and physical store ceiling. The broker stages the repository archive, walks it to select and pack files, reopening it when uncaptured rule files must be read, and emits a gzip tarball with `package/` paths, fixed timestamps and owner IDs, and normalized file modes. It runs no lifecycle scripts; build required output before tagging, or build and publish from CI. <!-- source: packages/plugin-github/src/provider.ts --> <!-- source: packages/core/src/ingest/dist-fetch.ts --> <!-- source: packages/core/src/registry/npm/tarball-pack.ts -->

GitHub archives apply `.gitattributes` export rules; files omitted there cannot be restored by npm inclusion rules. Generic Git also applies export-ignore rules. The broker does not resolve LFS pointers: a pointer in the input archive remains a pointer in the packaged files. <!-- source: packages/plugin-github/src/provider.ts --> <!-- source: packages/core/src/ingest/vcs/git-provider.ts --> <!-- source: packages/core/src/ingest/vcs/git-tar.ts -->
<!-- verify: npm-github-archive — on a disposable GitHub repository, check export-ignore and the repository's LFS archive setting; confirm the downloaded tarball contains the intended bytes before relying on ingest. -->

The packer honors root `files`, `main`, `bin` and bundled dependencies, directory `.npmignore` files with `.gitignore` fallback, and mandatory include/exclude rules. It skips symlinks. Its supported pattern grammar is literals and backslash escapes, `*`, `?`, whole-segment `**`, non-nested brace lists of at most 16 alternatives, ASCII bracket classes, leading `!`, and leading or trailing `/`. Brace ranges, nested braces, POSIX classes and extglobs skip the version with `candidate_skipped: unsupported_files_pattern`. Publish such packages from CI instead. <!-- source: packages/core/src/registry/npm/packlist-rules.ts --> <!-- source: packages/core/src/registry/npm/tarball-pack.ts -->

Packing bounds path depth at 64 segments and compiled rules at 4 MiB. Permanent pack refusals use `too_large`, `unsupported_files_pattern`, `invalid_packlist`, `invalid_tarball` or `archive_changed`; they record the reason in the source's error field and end that job without retrying the refusal. Size limits use `too_large`; other refusals include unsupported patterns, invalid packlists, malformed archives and invalid README controls. Exhausting the job attempts records the fixed code `internal`. These reports set the source error without counting as a poll failure. <!-- source: packages/core/src/registry/npm/packlist-rules.ts --> <!-- source: packages/core/src/ingest/dist-fetch.ts --> <!-- source: packages/core/src/sources/source-error-codes.ts --> <!-- source: packages/core/src/registry/module.ts --> <!-- source: packages/db-sqlite/src/repositories/source.ts -->

After packing, promotion stores a non-refetchable archive and attachment records its integrity and root README for the version. Until attachment, metadata has no built integrity and the archive endpoint waits for a build. A build that loses attachment leaves its promoted blob for orphan collection after seven days. Back up these bytes as described in [Backup and upgrades](../operations/backup-and-upgrades.md); retaining the Git repository alone is insufficient. <!-- source: packages/core/src/ingest/dist-fetch.ts --> <!-- source: packages/core/src/registry/npm/render.ts --> <!-- source: packages/core/src/registry/dist-service.ts --> <!-- source: packages/db-sqlite/src/repositories/blob-references.ts -->

## Choose GitHub repositories in the UI

Organization source managers can open **Packages → Add package**, choose **npm**, then choose **Choose GitHub repositories** under **From a connected GitHub organization**. This creates shared organization sources; projects attach the sources to use their packages. Members without `org:sources:write` see a prompt to ask a source manager.

Choose a connection by its existing source names and installation number. If none is available, follow **Add a GitHub source** and create an organization GitHub source with GitHub App authentication first. Set an optional repository name pattern (default `*`) and optionally enable **Include forks**, then choose **Preview repositories**. Review **Will be added**, **Already added** and **Skipped**; each skipped repository explains what prevents import. **Load more** follows the plan cursor and replaces the current preview page.

Select up to 20 repositories per import, individually or with **Select all on page**, then choose **Import selected**. The UI follows `remainingRepositories` automatically, shows progress, and retains each repository's result. Use **Retry failed repositories** for failures; if the upstream cannot make progress, the UI stops and offers retry rather than looping. Changing connection or discovery settings clears only the preview and requires another review; import results and failed retries stay visible. **Start over** clears the preview, results and progress. If GitHub rate limits imports, choose **Continue import** when it is available again. **Back** returns to the add-package choices.

API callers first use `GET /_pb/sources/discovery/connections` with an organization session holding `org:sources:write`. It returns up to 100 connection `items` containing an opaque `credentialId`, numeric `installationId`, up to five `sourceNames`, and the full `sourceCount`. Only organization-owned, organization-level GitHub App credentials referenced by organization GitHub sources appear. Credential material is never decrypted by this read. Pass the selected credential and installation to `POST /_pb/sources/discovery/plan`, then import the reviewed repositories with `POST /_pb/sources/discovery/apply`. Set `ecosystem` to `npm` in both calls. <!-- source: packages/core/src/api/routes/source-discovery-schemas.ts --> <!-- source: packages/db-sqlite/src/repositories/discovery-connections.ts --> <!-- source: packages/ui/src/pages/packages/discovery-picker.ts -->

## Manage saved discovery rules in the admin UI

Open **Sources** at organization scope and find **Discovery rules**. Source managers can choose **Create discovery rule**, enter a name, select a named GitHub connection, choose the ecosystem and repository pattern, include forks if needed, and set the interval and enabled state. The interval ranges from one hour to 30 days. Saving a new rule or changing its GitHub connection may ask you to sign in again; review and explicitly confirm the held action afterward.

From the GitHub repository picker, **Keep this selection up to date** opens a new rule with the selected connection, ecosystem, pattern and forks. A rule covers every matching repository, including future matches; the picker's individual checkboxes do not limit it. Rules create shared organization sources. Attach those sources to projects to use their packages.

The list shows the schedule, last completed counts and skipped repositories with explanations. Source managers also see current-run counts, repositories remaining in the current page, whether more pages remain, and GitHub rate-limit deadlines. Members with source-read permission see a summary without connection or progress details and cannot change rules. **Run now** requests a scan on a scheduler tick; it does not mean the scan finished and does not bypass GitHub backoff. Reload the list to check progress.

Use **More** to edit, enable, disable or delete a rule. Changing the connection, ecosystem, pattern or forks restarts its scan; changing its name or interval preserves progress. Disabling stops an active scan. Deletion asks for confirmation and leaves imported sources in place. If someone changes the rule while you edit, your draft stays visible beside the newer rule; choose **Use latest settings and review** before saving again. Duplicate names require another name.

Last-run details retain up to 50 skip explanations. The saved-rule API retains failure counts and a run-level failure reason, but no completed per-repository failure list. Per-repository failures are not retained.
