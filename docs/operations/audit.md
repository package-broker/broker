Audit is composed at build time. Core owns event sanitization, transactional staging, sequence assignment, hashing, delivery state, retention, the disposition ledger and health. `@package-broker/plugin-audit-trail` supplies browsing and verification access; `@package-broker/plugin-audit-otlp` and `@package-broker/plugin-audit-webhook` supply encoders and delivery protocols. An export-only broker still uses the database journal as a queue. Sequence numbers describe seal order, not the order of event timestamps. <!-- source: packages/core/src/audit/sealer.ts:1 --> <!-- source: packages/core/src/audit/export.ts:1 --> <!-- source: packages/db-sqlite/src/repositories/audit-seal.ts:575 -->

## Choose a mode

These are the audit-related parts of `broker.config.ts`; retain your platform, other plugins and platform ports. Imports are:

```ts
import { auditTrail } from '@package-broker/plugin-audit-trail';
import auditOtlp from '@package-broker/plugin-audit-otlp';
import auditWebhook from '@package-broker/plugin-audit-webhook';
```

| Intent      | Audit plugins                                                     | Audit configuration                                             | Reported mode                              |
| ----------- | ----------------------------------------------------------------- | --------------------------------------------------------------- | ------------------------------------------ |
| Local trail | `auditTrail()`                                                    | `audit: { policy: 'availability' }`                             | `trail`                                    |
| Export only | `auditWebhook({ id: 'archive', durableAck: true })`               | Same policy; configure receiver URL and credential              | `export`                                   |
| Both        | `auditTrail(), auditWebhook({ id: 'archive', durableAck: true })` | Same policy; configure receiver                                 | `trail`, with sink state listed separately |
| None        | No audit plugins                                                  | `audit: { policy: 'availability', acceptNoDurableAudit: true }` | `none`                                     |

With no explicit audit plugins and no acceptance, `pb build` adds the trail. Both sink factories default to `activation: 'build'`, `sourceIp: 'include'` and **delivery custody**, not durable custody. Set `durableAck: true` only after qualifying the receiver. OTLP defaults to 100 events per batch; webhook `skipAfter` defaults to three: under availability, a rejected record is retried while its rejection count is at most three and disposed after the fourth rejection. Required policy blocks instead. <!-- source: packages/core/src/audit/export-rejections.ts:178 --> <!-- source: packages/cli/src/build.ts:1 --> <!-- source: packages/plugin-audit-otlp/src/index.ts:137 --> <!-- source: packages/plugin-audit-webhook/src/index.ts:165 --> <!-- source: packages/core/src/audit/export-state.ts:1 -->

The prebuilt Node and Cloudflare distributions compile the trail with `toggleEnv: 'PB_AUDIT_TRAIL'` and both sinks with `activation: 'env'`, ids `otlp` and `webhook`, and availability policy. They do not assert durable acknowledgements. A custom build is needed to assert durable custody or change sink options. <!-- source: broker.config.ts:9 -->

| --------------- | -------------------------------------------------------------------------------------------------------------------- |
| Trail           | Leave `PB_AUDIT_TRAIL` unset or set `on`; leave sink endpoints unset                                                 |
| Both            | Keep trail on; configure either or both sink endpoints and credentials                                               |
| Export only     | `PB_AUDIT_TRAIL=off`; configure a sink                                                                               |
| None            | `PB_AUDIT_TRAIL=off`, no sink endpoint (including inherited OTEL endpoints), `PB_AUDIT_ACCEPT_NO_DURABLE_AUDIT=true` |

| Control                            | Precedence and accepted values                                                                                                                                                      |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PB_AUDIT_POLICY`                  | `required` raises build policy; `availability` cannot lower build or stored `required`. Any other value fails validation. Stored `required` wins on later boots.                    |
| `PB_AUDIT_TRAIL`                   | Exactly `on` or `off` when a trail declares this toggle; unset means on. Ignored under effective required policy.                                                                   |
| `PB_AUDIT_ACCEPT_NO_DURABLE_AUDIT` | Exactly `true` or `false`; build acceptance or environment `true` accepts none. Build acceptance is the reported source when both accept. Acceptance is incompatible with required. |

Required needs an active trail or an active durable sink, an alert route (configured observability endpoint or `audit.alerts.webhookEnv`) and a journal budget. Cloudflare defaults to 4 GiB; Node has no default, so set `audit.capacity.maxJournalBytes` in a custom build. Minimum budget is 64 MiB. Stored policy is a ratchet: lowering it requires `pb audit policy set availability`; also remove any build/environment requirement or the next boot raises it again. A fresh organization starts with the schema's availability default; the empty-chain initializer can then write its first effective policy (including required) and mode without a ledger row or audit event. Later transitions/raises are recorded. <!-- source: packages/core/src/audit/effective.ts:121 --> <!-- source: packages/core/src/audit/effective.ts:238 --> <!-- source: packages/core/src/audit/config.ts:12 --> <!-- source: packages/db-sqlite/migrations/0011_audit.sql:1 --> <!-- source: packages/db-sqlite/src/repositories/audit-effective.ts:1 -->

None must be explicitly accepted. It raises persistent `audit.mode_none` and warns: “Security events are not durably retained by this broker. Exporting previous history does not cover future activity.” Acknowledgement or export does not clear an active none condition. Required refuses none. Mode transitions are fenced by build generation and record mode/cutover evidence before retention can delete history. ### Destination environment precedence

Use `k=v,k=v` headers with percent-encoded values, for example `Authorization=Bearer%20RECEIVER_TOKEN`. Store real values in the deployment secret store. URLs must contain no credentials, query or fragment; redirects are refused. Public destinations require HTTPS and a credential header. Node can opt named sink ids into private egress with `audit.egress.allowPrivate`; that exception also permits private HTTP and headerless transport. Restrict it to a trusted local receiver. ## Sink lifecycle and commands

Sinks are reconciled by id, build generation and a URL fingerprint that excludes credentials. Credential rotation keeps the receiver identity. Missing definitions become disabled; an env sink with no destination is inactive. A change of receiver URL, plugin, kind or durable-custody declaration is recorded as a rebind. Only a receiver fingerprint change emits a receiver-changed marker; a plugin, kind or `durableAck` change with the same fingerprint records the rebind without that marker; review custody before accepting a new archive. Disabled sinks can still hold retention until retired. Retirement relinquishes their outstanding range, not the receiver's archive. An active sink also requires a configured deployment id (`DEPLOYMENT_ID` in the prebuilt configuration). Older build generations are fenced; use a generation at least as new as the stored sink generation when rebuilding or restoring. <!-- source: packages/core/src/audit/sinks/registry.ts:1 --> <!-- source: packages/runtime-node/src/audit.ts:159 -->

Build generation normally uses wall-clock milliseconds. With `SOURCE_DATE_EPOCH`, it is the epoch in seconds multiplied by 1000. Switching from wall-clock builds to an older pinned epoch therefore produces a stale generation that is fenced, even after a successful rebuild. <!-- source: packages/cli/src/manifest.ts:20 -->

Sink, policy and alert commands require exactly the highest stored sink generation for the organization, or `0` when it has no sink rows, and an active organization user or service principal. This can differ from the deployed build generation, especially for a trail-only installation. Read it directly with the organization-scoped query below using SQLite or the deployment platform’s D1 SQL console, then pass it as `--generation`. A lower value is stale; a higher value is refused as `generation_ahead`. <!-- source: packages/core/src/audit/sink-admin.ts:92 --> <!-- source: packages/db-sqlite/src/repositories/audit-health.ts:98 -->

```sql
SELECT coalesce(max(generation), 0) AS generation
FROM audit_sink WHERE org_id = 'ORGANIZATION_ID';
```

Replace the placeholder values in these examples. Cloudflare substitutes `--cloudflare --database-id DATABASE_ID` for `--sqlite broker.sqlite`, with `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN` in the environment. These are privileged direct database commands; protect database and platform credentials. <!-- source: packages/cli/src/commands/audit-sink.ts:45 -->

`cutover --register` accepts any nonnegative safe-integer generation at least as high as every stored sink generation for the organization; with no sinks, `0` is sufficient. It also requires an active organization user or service principal. `epoch bump` takes target flags only, with neither generation nor actor flags. <!-- source: packages/db-sqlite/src/repositories/audit-cutover.ts:54 --> <!-- source: packages/db-sqlite/src/repositories/audit-cutover.ts:73 --> <!-- source: packages/cli/src/commands/sqlite.ts:275 -->

| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sink list`                                  | Read-only states, progress, custody, generations and retirement confirmation. No ledger row or event.                                                                                                                       |
| `sink rebind ID --from N`                    | Rewinds progress/custody to `N-1`; ledger `rebind`. Requires a retained range and no outstanding in-flight body or unresolved rejection representation.                                                                     |
| `sink retire ID --confirm ID:FROM-TO`        | Only disabled/inactive sinks with a nonempty outstanding range. Use the exact confirmation from list; ledger `retire`.                                                                                                      |
| `sink unblock ID`                            | Retries a blocked sink after repairing its receiver; ledger `unblock`. Cannot clear a fork.                                                                                                                                 |
| `sink skip ID --seq N`                       | Disposes the eligible in-flight event using a tombstone; ledger `skipped`. This is visible loss, not a durable copy of the original.                                                                                        |
| `sink replay ID --from N`                    | Rewinds retained evidence; ledger **`rebind`**, reason `replay`. Records intent, not recovery.                                                                                                                              |
| `sink resolve ID --ledger-id ID`             | After durable ACK coverage, resolves an unresolved withheld/uncertain range with a `replay` ledger row carrying `resolves_id`. Does not erase the original incident.                                                        |
| `sink confirm-restore --from N`              | Clears restore hold, rewinds affected cursors/custody, queues fork markers; ledger `restore_confirmed` plus any discarded in-flight dispositions.                                                                           |
| `policy set required\|availability`          | Changes stored policy; ledger `policy_change`. Setting the same policy is a no-op. No `--confirm` flag exists. Required refuses effective none/export without a durable witness. Boot validates budget and alert route too. |
| `epoch bump`                                 | Marks restore pending, advances epoch/incarnation, clears verification and blocks active sinks; ledger `epoch_bump`, system `audit.sink_admin` event. It takes target flags only.                                           |
| `export`                                     | Each successful API page records ledger `export` (`api_export`) and an `audit.export` event. CLI verifies a pinned JSONL artifact, including resumable checkpoints.                                                         |
| `cutover --register FILE`                    | Verifies artifact custody against the database in effective none mode; ledger `export` (`verified_export`) and `audit.export` event. Registration does not clear none degradation.                                          |
| `alert list` / `alert ack CODE --revision N` | List is read-only. ACK stages `audit.sink_admin` with `alert_ack`, without a ledger row; stale revisions refuse.                                                                                                            |

## Restore and fork handling

Pause writers and consumers and preserve the database, keyring, configuration and external archive. The SQLite restore command marks audit restore state; for an out-of-band restore or a deployment clone, run `pb audit epoch bump` before delivery. Never run two writable clones with the same audit identity. Local cursor/hash checks and a webhook frontier ahead of, or inconsistent with, the local chain trigger a hold. OTLP has no frontier probe: rolling back both the database and cursor cannot reliably be detected through OTLP alone. <!-- source: packages/cli/src/commands/sqlite.ts:275 --> <!-- source: packages/core/src/audit/fork.ts:322 --> <!-- source: packages/plugin-audit-otlp/src/index.ts:28 -->

While `restorePending` is set, delivery and pruning are held and ordinary sink administration is refused; listing, policy handling and restore confirmation remain available. Compare retained history with the archive, establish the last common sequence/hash, then use `sink confirm-restore --from N`, where `N` is the first sequence to replay (at least the retained boundary and at most head plus one). Confirmation does not recreate missing bodies, clear unrelated blocks or certify the archive. It records the decision and sends fork markers; investigate unresolved loss separately. See [backup and upgrades](backup-and-upgrades.md) and [restore rehearsal](restore-rehearsal.md). <!-- source: packages/core/src/audit/sink-admin.ts:131 --> <!-- source: packages/core/src/audit/fork.ts:507 --> <!-- source: packages/db-sqlite/src/repositories/audit-prune.ts:1 -->

## Capacity and backpressure

Set a budget from peak events per second × tolerated outage seconds × measured bytes per record, plus catch-up, indexes, pending events, ledger, sink batches and the rest of the database. The budget uses logical journal bytes, not database file size. Payloads are capped at 4096 UTF-8 bytes, but envelope and index storage is additional. Availability can evict a sealed prefix, even with a trail, recording a capacity gap and markers. Pending events are not evicted. Required keeps evidence and enters refusal; normal mutations fail atomically with `503 audit_backlog_full`. The reserve is 1% of the configured budget, not extra disk magically provided by the runtime. Node availability without a budget has no capacity enforcement and warns at startup. <!-- source: packages/core/src/audit/capacity.ts:18 --> <!-- source: packages/db-sqlite/src/repositories/audit-prune.ts:157 --> <!-- source: packages/db-sqlite/src/repositories/audit-pending.ts:113 --> <!-- source: packages/core/src/audit/config.ts:1 -->

Reads remain available subject to normal authorization. Reserve actions include session operations except failed-login capture; token revoke/rotate; identity block and user/service-principal suspension; grant and project-grant revoke; source pause; setup completion and bootstrap-only role top-up; package unpublish, publish reject/expire and trusted-publisher disable; discovery-rule delete; registry-policy create/update/disable/release/membership replacement/expiry; notification disable/delete/credential replacement/automatic disable/delivery completion/cancellation; audit administration, export and mode changes. General role creation is subject to capacity refusal. Token rotation's issue companion and identity block's unlink companion also pass. This is a finite allowlist, not a guarantee that every security-related mutation succeeds; disk exhaustion can still fail writes. Failed login and access-denial recording is rate-limited best effort and must not change authentication responses. <!-- source: packages/db-sqlite/src/repositories/audit-pending.ts:6 --> <!-- source: packages/db-sqlite/src/repositories/audit-pending.ts:143 --> <!-- source: packages/core/src/audit/failure-events.ts:89 -->

## Health and alerts

Poll `GET /_pb/audit/status` for chain/epoch, retained boundary, actual verification scope, policy/mode source, capacity and sink progress/custody. Poll `GET /_pb/audit/health` with `org:audit:read` authority, including a suitably scoped service token. Alert on non-OK state and on the monitor losing access to this endpoint. These responses omit receiver URLs and credentials. Trail absence/inactivity returns `404 audit_trail_unavailable` on trail routes; status, health and administrator exports remain core services. <!-- source: packages/core/src/api/routes/audit-status.ts:1 --> <!-- source: packages/core/src/api/routes/audit.ts:1 -->

| Code                                                               | Response                                                                                                              |
| ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| `audit.skipped`, `audit.uncertain`, `audit.gap`, `audit.withheld`  | Investigate loss/disposition evidence; replay retained safe bodies where possible and resolve only after durable ACK. |
| `audit.marker_rejected`                                            | Repair receiver support for markers before unblocking.                                                                |
| `audit.blocked`, `audit.fork`                                      | Investigate rejection or restore/identity conflict; fork needs confirmation rather than unblock.                      |
| `audit.pending_old`                                                | Sealer pending age exceeded five minutes or timestamp is invalid; inspect job processing.                             |
| `audit.capacity`                                                   | Expand safe capacity, restore export throughput or reduce ingress; refusal is failing health.                         |
| `audit.mode_change`, `audit.policy_change`                         | Review configuration/operator changes and custody evidence.                                                           |
| `audit.sink_inactive`, `audit.config_invalid`                      | Inspect declared sinks, secrets and activation source.                                                                |
| `audit.mode_none`                                                  | No local trail or active sink; persistent degradation while none remains effective.                                   |
| `audit.chain_integrity`, `audit.hold_failed`, `audit.prune_anchor` | Investigate integrity, hold or retention-anchor failure before resuming deletion.                                     |

Health is `failing` for an active failing condition, otherwise `degraded` while a condition is active or its latest revision remains unacknowledged. Clearing the cause and acknowledging the current revision clears the incident; acknowledging an active condition does not repair it. Alerts emit fixed-code error logs (`audit.alert`) and `pb.audit.alerts_total{code}`; sending is best effort, persistent health is the backstop. ## Webhook receiver contract

POST envelopes contain `{v:1, chain_id, epoch, org_id, deployment_id, records:[...]}` with snake_case event/marker fields. Return `200 application/json` with `{"acked":{"chain_id":"...","epoch":0,"seq":123,"hash":"..."}}`, echoing the entire batch frontier, only after records, deduplication state and contiguous frontier commit atomically. A lost ACK causes repeat delivery. Deduplicate events by organization, chain, epoch and sequence; marker identities use `marker_id`. Same identity/hash is a no-op; conflicting content must alarm. Buffer or reject out-of-order records. Accept boundary, gap, tombstone, delivery-uncertain, withheld, fork, receiver-changed and head markers without treating a missing body as verified. Keep deduplication for the whole replay horizon and make late originals after tombstones safe and explicit. Give the broker append permission, never delete or retention-shortening permission. <!-- source: packages/plugin-audit-webhook/src/index.ts:78 --> <!-- source: packages/core/src/audit/plugin-api.ts:38 --> <!-- source: packages/core/src/audit/plugin-testing.ts:489 -->

The frontier probe is `POST {v:1, probe:"frontier", chain_id, org_id}`; it does not send epoch. Return `200 application/json {"frontier":null}` for no history, or a position with `chain_id`, `epoch`, `seq`, `hash`. Preserve the receiver frontier independently of broker restores. HTTP 400/422 are rejected, 413 is rejected/too-large; other non-200 responses retry. A malformed or mismatched ACK retries as `bad_response`. No request body is signed; authenticate and authorize the dedicated transport credential at the receiver. <!-- source: packages/plugin-audit-webhook/src/index.ts:94 --> <!-- source: packages/plugin-audit-webhook/src/index.ts:121 -->

## OTLP routing and durable acknowledgement qualification

Audit uses OTLP/HTTP JSON logs with scope name `package-broker.audit`, scope version `audit-otlp/1`, event names `package_broker.audit.<action>` and `package_broker.audit.marker.<kind>`, and `pb.audit.*` attributes. Route logs at the Collector ingress by that scope and event-name prefix into a separate audit pipeline/archive. Keep telemetry in its own pipeline; unexpected audit scope/version/name combinations should alert or quarantine, never silently disappear. Disable sampling, filtering, truncation and lossy transformations on the audit path. Test routing with an event and every marker kind and independently decode archived wire fields. <!-- source: packages/plugin-audit-otlp/src/encode.ts:1 -->

The [ingress authentication example](otel-collector/ingress-auth.yaml) illustrates bearer authentication and TLS. [Loki](otel-collector/loki.yaml), [Elasticsearch](otel-collector/elasticsearch.yaml) and [Graylog](otel-collector/graylog.yaml) illustrate log destinations. [Tempo](otel-collector/tempo.yaml), [Prometheus](otel-collector/prometheus.yaml) and [InfluxDB](otel-collector/influxdb.yaml) illustrate other telemetry, not an audit archive guarantee. These examples are telemetry starting points: they include in-memory batching or discarded signal paths and do **not** qualify `durableAck`. Prefer a dedicated authenticated audit receiver/pipeline to prevent audit from entering those paths.

Before a custom build sets `auditOtlp({ id: 'archive', durableAck: true })`:

1. Pin the exact Collector distribution/version and archive exporter. Review their acknowledgement semantics and save the tested configuration with the deployment.
2. Put `file_storage` and the exporter's persistent sending queue on persistent media with monitored capacity. Trace the complete receiver-to-queue path: no asynchronous in-memory batching or successful response before persistence. An exporter merely having a persistent queue is insufficient evidence.
3. Block the archive, send identifiable test events/markers, receive ACKs, kill the Collector immediately and restart on the same storage. Verify every acknowledged identity/hash reaches the archive, with duplicates handled safely.
4. Fill the queue disk and separately make the archive reject requests permanently. Verify backpressure/refusal reaches the broker before any unsafe success; verify queue recovery, permissions and alert delivery. If the Collector ACKs and later drops rejected records, it fails this qualification.
5. Test partial rejection, restart during flush and loss of the ACK after commit. Retain the results; repeat after Collector/exporter/configuration changes. Leave `durableAck` false if any path can acknowledge volatile or discarded data.

OTLP success is transport acknowledgement; the broker cannot prove Collector durability. Partial rejection creates an uncertain range rather than replaying the whole batch automatically. HTTP 429/502/503/504 retry; other non-success statuses reject. A zero-rejection warning is recorded as accepted with warning. Review uncertain ranges and the archive before replay/resolution. <!-- source: packages/plugin-audit-otlp/src/index.ts:48 --> <!-- source: packages/core/src/audit/export.ts:1 -->
