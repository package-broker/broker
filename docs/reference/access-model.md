An organization grant and a project grant have different boundaries. An organization role can carry `project:*` permissions inherited by projects; a project grant does not grant organization administration. A token narrows the principal's rights; it cannot create rights the principal lacks. <!-- source: packages/core/src/authz/project-actor.ts:25 --> <!-- source: packages/core/src/authz/scope.ts:102 -->

## Roles and grants

These are the built-in role keys and their shipped names. Inspect custom role permissions before treating a custom role as equivalent. <!-- source: packages/core/src/authz/permissions.ts:71 -->

| Role key               | Shipped name         | Rights                                                                                                                                                                                                                                                    |
| ---------------------- | -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `organization_admin`   | Organization Admin   | All catalogued organization and project permissions. <!-- source: packages/core/src/authz/permissions.ts:101 -->                                                                                                                                          |
| `organization_auditor` | Organization Auditor | Read organization users, roles, grants, sources, tokens and audit records; read project details, grants, packages, sources, tokens and audit records. No publishing or administration writes. <!-- source: packages/core/src/authz/permissions.ts:108 --> |
| `project_owner`        | Project Owner        | Read and publish packages; manage project settings, grants, packages, sources, service principals and tokens; read project audit records. <!-- source: packages/core/src/authz/permissions.ts:123 -->                                                     |
| `project_developer`    | Project Developer    | Read project details, packages and sources; publish packages and issue project tokens. <!-- source: packages/core/src/authz/permissions.ts:139 -->                                                                                                        |
| `project_auditor`      | Project Auditor      | Read project details, grants, packages, sources, tokens and audit records. No publishing. <!-- source: packages/core/src/authz/permissions.ts:146 -->                                                                                                     |

Group grants match both the provider and group name. Membership evidence and the matching identity's validation evidence expire after 24 h; signing in refreshes evidence through the configured identity provider. A group name by itself does not grant access. <!-- source: packages/db-sqlite/src/repositories/access.ts:252 --> <!-- source: packages/db-sqlite/src/repositories/access.ts:311 --> <!-- source: packages/db-sqlite/src/kysely.ts:249 --> <!-- source: packages/core/src/auth/identity-login.ts:331 -->

## Token kinds

This is the shared token-kind table for client setup and CI recipes. Prefixes identify kinds; they are not usable credentials. <!-- source: packages/core/src/secrets/token-format.ts:3 -->

| Scope   | Allowed operations, subject to principal rights and project policy                                                                     |
| ------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `read`  | Read project details and packages. <!-- source: packages/core/src/authz/scope.ts:71 -->                                                |
| `write` | `read` plus publish packages. <!-- source: packages/core/src/authz/scope.ts:72 -->                                                     |

Only an `all` project-mode token with `full` scope can exercise organization permissions. A selected PAT binds 1 to 200 distinct projects; an all-project PAT follows the user's current and future project access. Issuing a PAT requires fresh reauthentication. <!-- source: packages/core/src/authz/scope.ts:102 --> <!-- source: packages/core/src/authz/pat-service.ts:85 --> <!-- source: packages/core/src/authz/pat-service.ts:228 -->

Token use checks revocation and expiry on each authentication. Revoking a token stops its subsequent use; it does not revoke another token or undo an archive already downloaded. Token revocation requires a user session. <!-- source: packages/core/src/authz/token-use.ts:102 --> <!-- source: packages/core/src/authz/token-revoke.ts:84 -->

## Project package visibility and source credentials

Installing requires both the right to read packages in the requested project and a package visible in that project. Credentials used to read a vendor source do not grant a developer or token access to the project. <!-- source: packages/core/src/catalogue/package-access.ts:73 --> <!-- source: packages/core/src/catalogue/visibility.ts:81 --> <!-- source: packages/db-sqlite/src/repositories/source.ts:135 -->

| Rule                                  | Effect                                                                                                                                                                                                                                                                                                                                                                   |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Project-owned source                  | Serves only its owner project in the same organization, including when an attachment to another project is present. <!-- source: packages/core/src/catalogue/visibility.ts:71 -->                                                                                                                                                                                        |
| Organization-owned source             | May serve attached projects. It is unsuitable for credentials that must belong to only one project. <!-- source: packages/core/src/catalogue/visibility.ts:71 -->                                                                                                                                                                                                        |
| Attached source and package selection | Visibility comes from an explicit package selection or the attached source's include/exclude patterns and package visibility flag. An explicit selection takes priority over pattern filtering. <!-- source: packages/core/src/catalogue/visibility.ts:86 -->                                                                                                            |
| Inactive project                      | Has no winning package. <!-- source: packages/core/src/catalogue/visibility.ts:147 -->                                                                                                                                                                                                                                                                                   |
| Public proxy                          | Cannot supply a name held by a non-proxy source in the organization or matching a registered name, even if the private package is invisible to the caller. <!-- source: packages/core/src/catalogue/visibility.ts:123 -->                                                                                                                                                |
| Metadata cache                        | Keys include the project, source, package revision and organization scope; cache fills validate the live visibility epoch. A cached document does not grant another project access. <!-- source: packages/core/src/catalogue/cache-keys.ts:12 --> <!-- source: packages/core/src/catalogue/cache-keys.ts:40 --> <!-- source: packages/core/src/platform/cache.ts:129 --> |
| Vendor credential                     | Must belong to the same organization and project as its source. Separate project sources can use different vendor credentials for the same repository URL. <!-- source: packages/db-sqlite/src/repositories/source.ts:135 -->                                                                                                                                            |

An authenticated actor outside a project's visibility receives 404; an actor who can see the project but lacks the required operation can receive 403. At the package boundary, an absent or invisible package receives 404. <!-- source: packages/core/src/authz/engine.ts:210 --> <!-- source: packages/core/src/kernel/kernel.ts:678 -->

## Worked examples

### Agency with three clients

Create projects `client-a`, `client-b` and `client-c`. Grant each project's SSO group the project developer role only in that project. Put each client's vendor credentials in a source owned by that client's project and attach that source only there. A developer in the first group cannot reach another project's source by guessing a package name or archive URL. <!-- source: packages/core/src/authz/permissions.ts:139 --> <!-- source: packages/db-sqlite/src/repositories/access.ts:252 --> <!-- source: packages/core/src/catalogue/visibility.ts:71 --> <!-- source: packages/core/src/registry/dist-service.ts:272 -->

**Who can install:** members of each project's group with fresh evidence and a usable session or package-reading token can install that project's visible packages. Organization admins and auditors also inherit package-read rights across projects; use group grants to separate project users, not to hide packages from organization administrators. <!-- source: packages/core/src/authz/permissions.ts:101 --> <!-- source: packages/core/src/authz/permissions.ts:108 --> <!-- source: packages/core/src/authz/project-actor.ts:25 -->

### Internal-only package

Keep `example/internal-tools` in a source owned by project `internal`. Grant the internal engineering group the project auditor role if it only installs packages. Do not grant an external group access to `internal`. The source ownership rule keeps that package outside other projects. <!-- source: packages/core/src/authz/permissions.ts:146 --> <!-- source: packages/core/src/catalogue/visibility.ts:71 -->

**Who can install:** the internal group and organization roles inheriting package-read rights, with usable credentials. A token bound only to a different project cannot install from `internal`. <!-- source: packages/core/src/authz/scope.ts:102 --> <!-- source: packages/core/src/authz/permissions.ts:101 -->

### Customer-facing token

A proposed customer cut-off such as `2026-10-01` cannot currently be expressed through a usable customer token. The parser recognizes the customer prefix, but the authentication gate rejects it. A service token has no customer cut-off semantics. <!-- source: packages/core/src/secrets/token-format.ts:59 --> <!-- source: packages/core/src/authz/token-use.ts:102 --> <!-- source: packages/core/src/authz/service-token-service.ts:150 -->

**Who can install:** nobody using a customer token at this revision. A separately issued service token can install only within its stored permissions, binding and scope, without a customer cut-off. <!-- source: packages/core/src/authz/scope.ts:102 -->

## What is not enforced

Customer-token access and customer cut-offs are not implemented in the authentication path. The built-in roles above are the shipped roles; there are no built-in organization owner/member or project maintainer/reader roles under those names. Identity evidence expiry is enforced locally, but this does not establish a universal delay for detecting removal at an identity provider: this revision does not supply unattended daily identity-provider revalidation. Sign in again when PAT evidence becomes stale. <!-- source: packages/core/src/authz/token-use.ts:102 --> <!-- source: packages/core/src/authz/permissions.ts:71 --> <!-- source: packages/core/src/authz/pat-validation.ts:34 --> <!-- source: packages/db-sqlite/src/kysely.ts:249 -->
