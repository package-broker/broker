An organization role can carry `project:*` permissions inherited by projects; a project grant does not grant organization administration. A token narrows the principal's rights; it cannot create rights the principal lacks. <!-- source: packages/core/src/authz/project-actor.ts:25 --> <!-- source: packages/core/src/authz/scope.ts:102 -->

## Project package visibility and source credentials

Installing requires both the right to read packages in the requested project and a package visible in that project. Credentials used to read a vendor source do not grant a developer or token access to the project. <!-- source: packages/core/src/catalogue/package-access.ts:73 --> <!-- source: packages/core/src/catalogue/visibility.ts:81 --> <!-- source: packages/db-sqlite/src/repositories/source.ts:135 -->

| Rule                                  | Effect                                                                                                                                                                                                                                                                                                                                                                   |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Project-owned source                  | Serves only its owner project in the same organization, including when an attachment to another project is present. <!-- source: packages/core/src/catalogue/visibility.ts:71 -->                                                                                                                                                                                        |
| Organization-owned source             | May serve attached projects. It is unsuitable for credentials that must belong to only one project. <!-- source: packages/core/src/catalogue/visibility.ts:71 -->                                                                                                                                                                                                        |
| Attached source and package selection | Visibility comes from an explicit package selection or the attached source's include/exclude patterns and package visibility flag. An explicit selection takes priority over pattern filtering. <!-- source: packages/core/src/catalogue/visibility.ts:86 -->                                                                                                            |
| Inactive project                      | Has no winning package. <!-- source: packages/core/src/catalogue/visibility.ts:147 -->                                                                                                                                                                                                                                                                                   |
| Public proxy                          | Cannot supply a name held by a non-proxy source in the organization or matching a registered name, even if the private package is invisible to the caller. <!-- source: packages/core/src/catalogue/visibility.ts:123 -->                                                                                                                                                |
| Metadata cache                        | Keys include the project, source, package revision and organization scope; cache fills validate the live visibility epoch. A cached document does not grant another project access. <!-- source: packages/core/src/catalogue/cache-keys.ts:12 --> <!-- source: packages/core/src/catalogue/cache-keys.ts:40 --> <!-- source: packages/core/src/platform/cache.ts:129 --> |
| Vendor credential                     | Must belong to the same organization and project as its source. An authenticated actor outside a project's visibility receives 404; an actor who can see the project but lacks the required operation can receive 403. ## npm claims, publishing and admission

Hosted npm packages belong to the organization. A hosted source claims exact lowercase package names or scoped wildcards such as `@scope/*`; unscoped wildcards are refused. Claims for hosted and npm VCS sources are checked against other npm source claims in the same organization, in both directions, and against cached public packages. A claim suppresses npmjs proxy fallback immediately, even when its source is paused or the private package is invisible to a caller. <!-- source: packages/core/src/sources/claim-admission.ts --> <!-- source: packages/db-sqlite/src/repositories/registered-name.ts --> <!-- source: packages/db-sqlite/src/repositories/catalogue-predicates.ts -->

When an npmjs proxy exists in the organization, exact-name admission sends `HEAD https://registry.npmjs.org/<name>` through the outbound fetch policy; a scoped name encodes its slash as `%2F`. This reveals the proposed exact package name to the public registry. HTTP 200 refuses the claim as `name_public`; only HTTP 404 verifies absence. Other statuses, redirects, network failures and the five-second timeout fail closed as `name_public_unverified`. Wildcard claims skip this probe: cached names are checked, but an uncached public package under that scope can be hidden. <!-- source: packages/db-sqlite/src/repositories/registered-name.ts --> <!-- source: packages/core/src/registry/module.ts --> <!-- source: packages/core/src/sources/claim-admission.ts -->

Publishing requires a claimed name on an active hosted source, a usable write or full token, and either `project:packages:write` or `org:packages:publish` through the route's organization alternative. Both paths require current admission through the route project. Token project binding and project policy still apply. A source attachment alone does not establish package admission. Workload tokens additionally bind publishing to one exact name. <!-- source: packages/core/src/registry/npm/publish-service.ts --> <!-- source: packages/core/src/authz/scope.ts --> <!-- source: packages/core/src/authz/engine.ts --> <!-- source: packages/db-sqlite/src/repositories/catalogue-publish-guard.ts -->

The package setting has three modes; source attachment and normal project read authority remain necessary for installs. Existing explicit package memberships are separate from this default for new projects. <!-- source: packages/core/src/catalogue/visibility.ts --> <!-- source: packages/db-sqlite/src/repositories/visibility-derive.ts -->

| Mode             | Stored setting                                                       | Effect                                                                                                                                            |

| Available        | `visible_to_new_projects = 1`                                        | Eligible through the attached source's selection rules. <!-- source: packages/core/src/catalogue/visibility.ts -->                                |
| Require approval | `visible_to_new_projects = 0`, `new_project_access_mode = 'request'` | An eligible project can request an explicit membership. <!-- source: packages/db-sqlite/src/repositories/package-access-requests.ts -->           |

## Publish approval and scanning

The hosted source's `require_publish_approval` holds new versions until a user with `org:packages:approve` approves them. The project's similarly named flag is reserved. User publishes cannot be self-approved; service-token publishes are exempt, with the token ID retained in audit attribution. Pending publishes are inspected through the publishes API; held versions, including a held first package, remain absent from ordinary package readers. <!-- source: packages/core/src/registry/npm/publish-service.ts --> <!-- source: packages/core/src/api/routes/publishes.ts --> <!-- source: packages/core/src/api/routes/publishes-schemas.ts --> <!-- source: packages/db-sqlite/src/repositories/catalogue-predicates.ts --> <!-- source: packages/core/src/api/routes/projects-schemas.ts -->

Configured publish-policy hooks add a separate persisted scan gate, recording the required scanner IDs at publish time. Builds compose at most three scanners; the job invokes them in order with a 60-second timeout for each. All must allow before the scan gate opens, and any approval gate must also be satisfied before activation. Exceptions and timeouts retry up to three attempts, then fail closed; missing scanners also fail closed. An authorized approver can rescan or reject a failed scan. <!-- source: packages/core/src/registry/npm/publish-service.ts --> <!-- source: packages/core/src/ingest/publish-scan-job.ts --> <!-- source: packages/cli/src/manifest.ts --> <!-- source: packages/db-sqlite/src/repositories/publishes.ts --> <!-- source: packages/core/src/api/routes/publishes.ts -->

A scan denial tombstones the version and removes it from pending-publish lists; approve and reject then return `already_decided`. Its pending approval record closes through expiry. Rejection and approval expiry also tombstone held versions. Decisions use revision checks and database fences with their audit writes, and approval does not bypass the scan gate. <!-- source: packages/core/src/api/routes/publishes.ts --> <!-- source: packages/db-sqlite/src/repositories/publishes.ts --> <!-- source: packages/core/src/ingest/publish-approval-expire-job.ts -->

## Web login and trusted publishing

npm web login opens a browser confirmation for the selected project. A freshly reauthenticated user chooses read or write scope, and confirmation issues a project-bound PAT. The token is sealed while awaiting collection and delivered to one successful CLI poll; expired uncollected tokens are revoked. Logging in does not grant publishing authority or bypass package admission. See the [client guide](../clients/npm-pnpm-yarn.md) for client support. <!-- source: packages/core/src/api/routes/npm-login.ts --> <!-- source: packages/core/src/authz/pat-service.ts --> <!-- source: packages/db-sqlite/src/repositories/npm-login.ts --> <!-- source: packages/db-sqlite/src/repositories/npm-login-expire.ts -->

Trusted publishing exchanges a verified workflow identity for a 15-minute workload token bound to one npm package. Matching includes numeric repository and owner IDs, the caller workflow, environment and any configured ref restriction; issuance records replay protection atomically. Disabling the publisher revokes its live workload tokens. Publish approval and scan gates still apply. See [npm trusted publishing](../guides/npm-trusted-publishing.md) and the [configuration reference](configuration.md). <!-- source: packages/core/src/registry/npm/oidc/exchange.ts --> <!-- source: packages/db-sqlite/src/repositories/trusted-publishers.ts --> <!-- source: packages/core/src/authz/service-token-service.ts --> <!-- source: packages/core/src/registry/npm/publish-service.ts -->

Manage trusted publishers in **Tokens → Trusted publishers** or through `/_pb/trusted-publishers`: GET lists bindings, POST creates one, PUT on `/:id` edits one, and DELETE on `/:id` disables one. These operations require a human session with `org:service-principals:write`; writes also require `org:packages:publish`, and edits and disables require the current revision. Creation atomically adds a service identity and its publish permission. Its label includes the repository, workflow and an eight-character hash of the binding fields, with bounded shortening and a validated fallback; the label does not determine trust. See [Configure a publisher](../guides/npm-trusted-publishing.md#configure-a-publisher) for the exact naming rules and repository connection requirements. <!-- source: packages/core/src/api/routes/trusted-publishers-schemas.ts --> <!-- source: packages/core/src/api/routes/trusted-publishers.ts --> <!-- source: packages/core/src/api/routes/trusted-publishers-name.ts --> <!-- source: packages/db-sqlite/src/repositories/trusted-publishers.ts --> <!-- source: packages/ui/src/pages/tokens/trusted-publishers.tsx -->

## Worked examples

### Agency with three clients

Create projects `client-a`, `client-b` and `client-c`. Grant each project's SSO group the project developer role only in that project. Put each client's vendor credentials in a source owned by that client's project and attach that source only there. A developer in the first group cannot reach another project's source by guessing a package name or archive URL. <!-- source: packages/core/src/authz/permissions.ts:139 --> <!-- source: packages/db-sqlite/src/repositories/access.ts:252 --> <!-- source: packages/core/src/catalogue/visibility.ts:71 --> <!-- source: packages/core/src/registry/dist-service.ts:272 -->

**Who can install:** members of each project's group with fresh evidence and a usable session or package-reading token can install that project's visible packages. Organization admins and auditors also inherit package-read rights across projects; use group grants to separate project users, not to hide packages from organization administrators. <!-- source: packages/core/src/authz/permissions.ts:101 --> <!-- source: packages/core/src/authz/permissions.ts:108 --> <!-- source: packages/core/src/authz/project-actor.ts:25 -->

### Internal-only package

Keep `example/internal-tools` in a source owned by project `internal`. Grant the internal engineering group the project auditor role if it only installs packages. Do not grant an external group access to `internal`. The source ownership rule keeps that package outside other projects. <!-- source: packages/core/src/authz/permissions.ts:146 --> <!-- source: packages/core/src/catalogue/visibility.ts:71 -->

**Who can install:** the internal group and organization roles inheriting package-read rights, with usable credentials. A token bound only to a different project cannot install from `internal`. <!-- source: packages/core/src/authz/scope.ts:102 --> <!-- source: packages/core/src/authz/permissions.ts:101 -->

### Customer-facing token

Customer tokens cannot authenticate or enforce a customer cut-off. The parser recognizes the customer prefix, but the authentication gate rejects it. A service token has no customer cut-off semantics. <!-- source: packages/core/src/secrets/token-format.ts:59 --> <!-- source: packages/core/src/authz/token-use.ts:102 --> <!-- source: packages/core/src/authz/service-token-service.ts:150 -->

**Who can install:** nobody using a customer token. A separately issued service token can install only within its stored permissions, binding and scope, without a customer cut-off. <!-- source: packages/core/src/authz/scope.ts:102 -->

## What is not enforced

The organization setting `token_ci_readonly_expiry_days` is not enforced by service tokens today; the service-token ceiling documented above comes from the code’s `tokens.maxLifetimeDays.service` policy. <!-- source: packages/db-sqlite/migrations/0001_init.sql:39 --> <!-- source: packages/core/src/authz/service-token-service.ts:280 --> <!-- source: packages/core/src/authz/service-token-service.ts:385 -->

Customer-token access and customer cut-offs are not implemented in the authentication path. Identity evidence expiry is enforced locally, but this does not establish a universal delay for detecting removal at an identity provider: the broker does not perform unattended daily identity-provider revalidation. Sign in again when PAT evidence becomes stale. <!-- source: packages/core/src/authz/token-use.ts:102 --> <!-- source: packages/core/src/authz/permissions.ts:71 --> <!-- source: packages/core/src/authz/pat-validation.ts:34 --> <!-- source: packages/db-sqlite/src/kysely.ts:249 -->
